# Ossie ⇄ SAP CSN converter

Converts between a SAP **CSN** document (Core Schema Notation, the JSON that
`cds compile --to csn` writes and SAP Datasphere exchanges) and an Apache Ossie
semantic model, in both directions. It works offline on files: it does not call
SAP.

```
ossie-sap-csn csn-to-ossie -i model.csn.json  -o semantic_model.yaml [--name NAME]
ossie-sap-csn ossie-to-csn -i semantic_model.yaml -o model.csn.json
```

Warnings (information the target cannot hold, or that was set aside) go to stderr,
one per line, as `[WARNING] <TYPE>: <element> — <detail>`. Input that cannot be
converted at all exits with status 1 and a message.

```
uv sync
uv run pytest
```

## CSN → Ossie

| CSN | Ossie |
|-----|-------|
| `entity` (table or view) | dataset; `source` is `@cds.persistence.name`, else the CSN name; the name drops the namespace unless two entities would collide |
| element | field; `type` resolves through user-defined types and `type of` references to a CDS built-in, then to an Ossie `datatype` |
| `key: true` | `primary_key` |
| `@assert.unique.*` | `unique_keys` |
| calculated element (`value`) | field expression, translated from CXN to ANSI SQL |
| `Association` / `Composition` with a target in the document | relationship, from the owning entity to the target |
| managed association | relationship, plus a field for each generated foreign-key column (`<assoc>_<key>`) |
| `@Aggregation.default` (`SUM`, `MIN`, `MAX`, `AVG`, `COUNT`, `COUNT_DISTINCT`) | metric over the element |
| `@Aggregation.default` + `@Ossie.metric: true` | metric over the element's expression; no field. Model-scoped, or dataset-scoped with `@Ossie.datasetMetric: true` |
| `@Ossie.metrics` on an entity | that dataset's `metrics`, as written |
| `@EndUserText.label`, `@Common.Label` | `label` |
| `doc`, `@EndUserText.quickInfo`, `@Common.QuickInfo` | `description` |
| a temporal type, or `@Semantics.businessDate` / `calendar` / `fiscal` | `dimension.is_time: true` |

Everything else — remaining annotations, `length`/`precision`/`scale`, the `query`
or `projection` of a view, types, services, actions and the root keys — is kept in a
`SAP_CSN` custom extension so the document exports back unchanged. So is the original
CXN of a calculated element: export reuses it as long as the field's expression is still
the SQL it was rendered as, and translates the SQL afresh once it has been edited.

A derived measure whose expression cannot be wrapped in an ANSI SQL aggregate (it does not
parse, or `@Ossie.sql` gives it in another dialect) is kept in the extension and reported as
`METRIC_NOT_MODELED`, rather than becoming a metric over a column that does not exist.

## Ossie → CSN

| Ossie | CSN |
|-------|-----|
| dataset | `entity` named by the `SAP_CSN` extension, else the dataset name |
| field | element; `datatype` → `cds.String`, `Integer`, `Decimal`, `Double`, `Boolean`, `Date`, `Time`, `Timestamp` |
| field expression other than its own column | calculated element (`value`), translated from SQL to CXN |
| relationship | association on the `from` entity: managed (`keys`) when its foreign-key fields were generated by one, otherwise an `on` condition. A composite key becomes an `and` of equalities |
| metric, one aggregate over a column of the same name | `@Aggregation.default` on that element |
| metric, one aggregate over an expression | derived measure element (`value` + `@Aggregation.default` + `@Ossie.metric`) |
| dataset metric (`datasets[].metrics`), one aggregate over the dataset's own fields | derived measure element of that entity, also marked `@Ossie.datasetMetric` |
| `unique_keys` | `@assert.unique.<name>` |

A derived measure may reach other datasets through relationships (`SUM(orders.qty * book.price)`),
because a relationship runs from the many side to the one side and so cannot fan out the rows
being aggregated.

### What CSN has no place for

* **Metrics CSN cannot express** — `COUNT(*)`, ratios of two aggregates, window functions,
  expressions over datasets no relationship connects, expressions CXN has no form for — are
  written to `meta.ossie.metrics` on the CSN root and reported as `METRIC_NOT_MODELED`. CSN
  consumers ignore `meta.ossie`; this converter reads it back. A dataset metric CSN cannot
  express goes to an `@Ossie.metrics` annotation on its entity instead, so it keeps its scope.
* **AI context and other vendors' custom extensions** ride in `@Ossie.aiContext` and
  `@Ossie.customExtensions` annotations. Model-level ones go to `meta.ossie.model`.
* **A field expression CXN cannot hold** (a window function, a subquery) is exported as a plain
  column with the original text in `@Ossie.sql`, and reported as `EXPRESSION_NOT_TRANSLATABLE`.
* **A key naming a column the dataset does not declare** is carried whole in `@Ossie.primaryKey`
  or `@Ossie.uniqueKeys`, and reported.
* **A field with no `datatype`** is exported as `cds.String`, because CSN requires a type, and
  reported as `ASSUMED_DATATYPE`.

Only the `ANSI_SQL` dialect is read. A field or metric that has only another dialect is reported
as `DIALECT_UNAVAILABLE` rather than guessed at.

## Limitations

* **CAP and Datasphere CSN.** The converter reads the annotations both write for analytics
  (`@Aggregation.default`, `@Analytics.dataCategory`, `@EndUserText.label`). It does not interpret
  Datasphere's analytic-model objects (fact sources, attribute and measure groups, variables) as
  such; they arrive as plain entities with their annotations preserved.
* **Not translated:** structured and array-typed elements, virtual elements, `$self` backlink
  associations (the forward association already is the relationship), associations whose target is
  not in the document, `on` conditions other than a conjunction of column equalities, and
  expressions with subqueries, `$session` or `$user`. Each is kept in the `SAP_CSN` extension and
  reported, never dropped silently.
* **Views.** A view's elements become fields and its `query` is preserved, but the converter does
  not interpret the query; the dataset `source` is the view's own name.
* **Export validity.** The converter does not run the CDS compiler. A CSN it writes follows the
  CSN schema but has not been compiled with `cds`.
* **Conversion is not a CDS or SQL migration.** Expressions are translated between SQL and CXN
  only for the constructs both express: references, literals, arithmetic, comparison, `AND`/`OR`/`NOT`,
  `IN`, `LIKE`, `BETWEEN`, `IS NULL`, `CASE`, `CAST` and plain function calls. A window function, a
  parameter reference or a token outside that list is refused and reported, never rendered without it.

### `CAST` types

Each CDS type a `cast` names has an SQL type that reads back as that same CDS type, with
`length`, `precision` and `scale` written as type parameters:

| CDS | SQL |
|-----|-----|
| `cds.String` (`length`) | `VARCHAR`, `VARCHAR(n)` |
| `cds.LargeString` | `CLOB` |
| `cds.Integer`, `cds.Int32` | `INT` |
| `cds.Int16` / `cds.Int64` | `SMALLINT` / `BIGINT` |
| `cds.Decimal` (`precision`, `scale`) | `DECIMAL`, `DECIMAL(p)`, `DECIMAL(p, s)` |
| `cds.Double` | `DOUBLE` |
| `cds.Boolean` / `cds.Date` / `cds.Time` | `BOOLEAN` / `DATE` / `TIME` |
| `cds.DateTime` (seconds) | `TIMESTAMP(0)` |
| `cds.Timestamp` (fractional seconds) | `TIMESTAMP` |

CDS defines `cds.Int32` as another name for `cds.Integer`, so SQL alone reads `INT` back as
`cds.Integer`; the CXN kept in the `SAP_CSN` extension preserves the `cds.Int32` spelling. Element
types never go through SQL: the original CDS type is kept in the extension, so `cds.DateTime`,
`cds.Int32` and `cds.LargeString` elements export back as they were.
